# 源泉徴収票の読取り・保存・検証の設計

作成日・一次資料の再確認日: 2026-10-08。状態: v1.0.0として実装・検証済み（架空資料と使い捨てDB）。調査起点: main、`3d08ae7`、v0.21.0。

この文書は、給与所得の源泉徴収票について、欄の取り違えと未確認値の流入を防ぐ設計である。製品コード・Skill・スキーマと旧DB移行処理をv1.0.0として実装し、架空票・使い捨てDBだけで検証した。実データのDBは移行・変更していない。架空画像の隣接二欄の誤読は前後とも未再現であり、合計検算の検出限界は維持する。固定資産台帳の段階4以降は、[既存の設計](fixed-asset-ledger-design.md)で別に進める。

## 1. 目的と範囲

原本の読取り、構造化、検算、確認、保存、読戻し、申告計算、DBとの照合を一つの経路として扱う。成功条件は、特定親族特別控除と社会保険料等の金額を別々に保持し、未確認を0へ変えず、誤った証憑を申告用データとして採用する前に止められることである。

初版の画像検証対象は、2025年分の改正後の給与所得の源泉徴収票（受給者交付用）と、同じ欄配置の2026年分とする。年末調整済み・未済の両方を扱う。年分と帳票の版は別に確認し、2025年中に発行された旧様式を、年分だけで改正後とみなさない。他の様式は読取り候補を保持できるが、対応を検証するまでは自動照合を完了扱いにしない。

2026年分の制度を使う検証用の年末調整済み票は、原則どおり同年12月以後に改正を適用するケースで作る。年途中の死亡・出国等による年末調整・準確定申告の経過措置は、自動組立ての対象へ加えない。同じ年分でも適用時点が異なることがあるため、原本の記載額を「現在の控除表と違う」という理由だけで書き換えない。

以下は対象外とする。

- OCRエンジンの開発・導入、画像認識モデルの固定、全帳票の座標テンプレート化。
- 退職所得・公的年金の源泉徴収票、税理士等の報酬の支払調書。
- 税率、控除額の表、端数処理、給与所得・人的控除の計算方法の変更。
- 源泉徴収票だけを使った扶養要件等の確定、年末調整の税額の自動訂正。
- 未払給与・未徴収税額がある票の申告入力の自動組立て。内書きを確認した時点で個別確認へ回す。
- 作成コーナーのブラウザ入力・送信。今回は転記項目の整理までを設計する。

これは当forkの改修であり、fork元への還流を前提にしない。実データを設計・テストに使わない。

### 2.2 帳票と税務上の境界

- 改正後の様式では、特定親族特別控除の欄は社会保険料等の欄の左隣にある。公開PDFを画像へ変換し、受給者交付用の欄配置を確認した。[様式PDF](https://www.nta.go.jp/taxes/tetsuzuki/shinsei/annai/hotei/pdf/r07/01.pdf)
- 社会保険料等の欄には小規模企業共済等掛金が含まれ、その掛金は内書きされる。内書きを合計に再加算しない。[記載要領](https://www.nta.go.jp/publication/pamph/hotei/tebikihtml/2-2-14.htm)
- 所得控除合計と基礎控除額は、年末調整済みの票に記載する項目である。年末調整未済の空欄を0円の適用額と解釈しない。[控除合計の記載要領](https://www.nta.go.jp/publication/pamph/hotei/tebikihtml/2-2-5.htm)、[基礎控除の記載要領](https://www.nta.go.jp/publication/pamph/hotei/tebikihtml/2-2-19.htm)
- 2025年分・2026年分の控除合計には特定親族特別控除を含める。Web版の控除合計の列挙だけに依存せず、年分が固定された年末調整資料の計算手順も確認する。2026年分では、特定親族特別控除と基礎控除がそれぞれ合計の構成項目として示されている。[令和7年分・3-5](https://www.nta.go.jp/publication/pamph/gensen/nencho2025/pdf/109.pdf)、[令和8年分・38ページ、3-5](https://www.nta.go.jp/publication/pamph/gensen/nencho2026/pdf/109.pdf)
- 2026年8月の税務署提出用の様式変更について、受給者交付用は変更されていないと案内されている。提出用の新様式を給与の受給者向け読取りへ一律に当てはめない。[F1-1](https://www.nta.go.jp/taxes/tetsuzuki/shinsei/annai/hotei/23100051.htm)

年末調整時の控除額と、給与以外の所得・追加控除も含めた確定申告時の控除額は別の値である。源泉徴収票の合計額を`IncomeTaxInput`へ上書きしたり、既存の人的控除計算へ特定親族特別控除を二重加算したりしない。

実装時のfixtureのREADMEには、資料ID、正式名称、発行主体、版・更新日、対象年分、適用時点、該当ページ・問番号、URL、取得日、取得PDFのSHA-256を残す。資料に改訂日の記載がない場合は「記載なし」とし、取得日で代用しない。Webページの更新で過去年分の根拠が入れ替わらないよう、年分が固定されたPDFを期待値の根拠にする。

### 2.4 公的資料で決まることと、このソフトで決めること

| 論点 | 公的資料から確認する事実 | このソフトの設計判断 |
|---|---|---|
| 未読と0の区別 | 記載すべき欄、その欄の額の意味、年末調整未済時の記載対象を確認する | 未読をNULLで保存する。旧値は保持し、今回の申告に使う票だけを再確認する。これはDBの再確認を法令が一律に義務付けているという意味ではない |
| 下書きと訂正 | 原本の記載額を正しく受け渡す必要がある | 下書きの保存、同じIDでの訂正、失敗時のロールバックを設ける。これらのCLI・DBの仕様を税法の要件とは呼ばない |
| 人数・区分からの額 | NTA-2025-TABLE／NTA-2026-TABLE等に従い、年齢・所得・同居等の条件を確認する | 初版では人数の自動認識を追加しない。既存関数と根拠を使う確認手順に絞る。公的資料があることと、各利用者の事実が確認できたことは分ける |
| 申告前検査 | 正しい年分・適用時点の額を使い、内数や前職分を重複計上しない | どの票を使ったかを明示し、未確認のまま申告前検査を合格にしない。試算の扱いやエラーの重大度は、本ソフトの契約として決める |

同じ票の同じ内容を確認済みなら、毎回確認を求めない。金額・年分・年末調整状態等を変更した場合は、変更後の内容を確認する。移行時に全年度の票の原本を一括で開く処理は設けない。

公的資料との不一致が既存の`tax_constants`や計算関数で見つかった場合は、資料・年分・再現条件を付けて別の欠陥として報告する。この読取り設計の実装中に、帳尻を合わせるために税計算や凍結期待値を変更しない。

| 方法 | 評価 |
|---|---|
| Skillの注意書きだけを直す | 変更は小さいが、未確認の保存とCLI経由の検査を解決できない |
| 型・保存・共通検算を揃え、既存の読取り手順につなぐ | 採用する。既存CLIと計算関数を再利用し、画像読取りと数値検算の責任を分ける |
| 帳票の認識・座標管理・証憑追跡を新しい基盤として作る | 初版には含めない。今回の誤りを防ぐための変更範囲を超える |

新しい外部依存や補助テーブルは追加しない。検算はDBアクセスを持たない関数にまとめ、保存前のプレビュー、保存時、一覧、sanity-checkから同じ関数を呼ぶ。税の金額を求める必要がある箇所は既存の年分別定数と計算関数を使い、別の税率表を作らない。

## 4. データの契約

### 4.1 共通の金額フィールド

3つの源泉徴収票モデルで、金額フィールドの名前と意味を揃える。共通定義を共有し、同じ一覧を3か所で手書きしない。全金額は非負の厳密な`int | None`とし、省略時は`None`にする。bool、float、数値文字列はモデルで拒否する。カンマ等の除去は読取り時の構造化で行い、CLIへ文字列を渡して型変換を期待しない。

| フィールド | 内容と変更 |
|---|---|
| `payment_amount`、`withheld_tax` | 既存名を維持し、票に記載された支払金額と源泉徴収税額を保持する |
| `social_insurance` | 既存名を維持する。源泉徴収票モデルでは「社会保険料等の金額」の総額であり、内書きを含む |
| `life_insurance_deduction`、`earthquake_insurance_deduction`、`housing_loan_deduction` | 既存の記載額を保持する。住宅ローン控除は所得控除合計へ加算しない |
| `spouse_deduction`、`basic_deduction` | 既存名を読取り結果にも公開する。票にある金額を保持する |
| `dependent_deduction` | 既存名を維持する。票に直接の金額欄はないため、人数・区分から確認した照合用の額とする |
| 生命保険料の既存5項目、`national_pension_premium`、`old_long_term_insurance_premium` | 名前を維持し、未確認を`None`にする。保険料と控除額を区別する |
| `specific_relative_special_deduction` | 新規。特定親族特別控除の記載額 |
| `total_income_deductions` | 新規。所得控除の額の合計額 |
| `salary_income_after_deduction` | 新規。給与所得控除後の金額（調整控除後） |
| `social_insurance_small_business_mutual_aid` | 新規。社会保険料等の欄の内書き額。総額とは別に保持する |
| `other_personal_deductions` | 新規。障害者・寡婦・ひとり親・勤労学生の控除を確認した照合用合計。特定親族特別控除、配偶者控除、扶養控除、基礎控除は含めない |

`dependent_deduction`と`other_personal_deductions`は、読めた直接の金額と混同しない。初版では人数・区分の自動認識と一括換算を新設せず、既存関数または該当年の手引きで額を確定する。確定できなければ`None`を返す。控除合計との差額から逆算して埋めてはならない。

これらの照合用の派生額の根拠には、資料ID・対象年分・人数と区分・計算過程を含める。金額を印字された欄から読んだ場合は、原本の記載額をそのまま保存し、控除表を使って上書きしない。

### 4.2 確認情報

| フィールド | 型・既定値 | 意味 |
|---|---|---|
| `document_fiscal_year` | 厳密な`int \| None`、省略時`None` | 原本から確認した年分。CLIの`--fiscal-year`と一致させる |
| `year_end_adjusted` | `StrictBool \| None`、省略時`None` | 年末調整済みならtrue、未済と確認した場合はfalse。空欄だけから推測しない |
| `source_confirmed` | `StrictBool \| None`、省略時`None` | ラベル・金額・年分・内書き・摘要を原本と照合した状態。falseは未完了が判明している状態、Noneは状態自体が未確認 |
| `blank_fields` | 共通金額フィールド名の列挙値のリスト、入力の省略時は空リスト | 原本で空欄と確認できた項目。空欄と未読を分ける |
| `deduction_derivation_note` | `str \| None`、省略時`None` | 人数・区分から求めた照合額の根拠。親族等の実名は不要 |
| `source_file` | 既存の`str \| None` | 原本の参照。エラーメッセージへ不用意に展開しない |

`blank_fields`にあるフィールドの金額は`None`でなければならない。明示された0は`0`のまま保持する。`None`かつ`blank_fields`にない項目は未読・未確認と扱う。重複した名前、未知の名前、数値と空欄の同時指定は拒否する。追加情報が黙って捨てられないよう、源泉徴収票の入力モデルは未知のキーも拒否する。

原本照合の完了は、実帳簿への登録の承認とは別である。`source_confirmed=true`だけを根拠に仕訳登録や申告送信を行わない。

### 4.3 空欄と0の扱い

原本の記録は変更せず、検算時にだけ有効値を作る。年末調整済みで空欄・不適用を確認できた配偶者・特定親族・生命保険・地震保険・社会保険料等とその内書きは、照合用に0と扱える。人数から求める二つの項目は空欄から0を作らず、対象者がいないことを確認して明示的な0を入力する。

社会保険料等とその内書きについては、年末調整未済でも、その票に含まれる控除がないことを原本で確認できた空欄に限り、照合用に0と扱える。票の外で支払った保険料・掛金がないことまで確認したとはみなさない。

支払金額、源泉徴収税額、年末調整済み票の控除合計・給与所得控除後の金額・基礎控除額は、空欄を0へ変換しない。0の記載または適切な資料による0の確認が必要である。その他の保険料内訳等の空欄も、計算に使う必要が生じた時点で確認する。

年末調整未済で合計額等が空欄の場合、控除合計の検算は「対象外」とする。「0と一致した」とは返さない。`source_confirmed=true`でも、必要項目が未確認なら利用可能にはならない。

## 5. 検算とCLI

### 5.1 共通検算

`tools/withholding.py`に、源泉徴収票と対象年を受け取る純粋な検算関数を置く。モデルと結果型は既存の規約に従って`models.py`に置く。検算結果はDBへ保存せず、呼出しのたびに算出する。

年末調整済みで必要な内訳が揃った場合だけ、次を照合する。

```text
内訳合計 = social_insurance
         + life_insurance_deduction + earthquake_insurance_deduction
         + spouse_deduction + dependent_deduction
         + specific_relative_special_deduction + basic_deduction
         + other_personal_deductions
差額 = 内訳合計 - total_income_deductions
```

社会保険料等の内書きと国民年金保険料は重ねて加算しない。住宅ローン控除、給与所得控除後の金額、所得金額調整控除もこの式に加えない。基礎控除の記載がない場合に、申告全体の所得から計算した額で穴埋めして一致させない。

結果は次の情報を持つ。

- `status`: `matched / mismatched / incomplete / not_applicable`。これは控除合計の検算状態である。年末調整状態が未確認の場合はincompleteにする。
- `reported_total`、`calculated_total`、`difference`: 円単位の値またはnull。全内訳が揃わなければ後者二つはnullとする。
- `missing_fields`: 未確認の項目名。
- `issues`: `severity`、`code`、`fields`、`message`を持つ一覧。
- `ready_for_calculation`: 証憑から給与の支払金額・源泉税額・社会保険料部分を取り出せる状態か。申告全体の準備完了を意味しない。

`ready_for_calculation=true`には、原本の年分との一致、年末調整状態の確定、原本照合の完了、支払金額と源泉税額の確定、社会保険料等と内書きの確定が必要である。年末調整済みの場合は控除合計の一致も必要になる。年末調整未済の場合は合計の検算が対象外でもよい。未払・未徴収の内書きや、対象外の様式等の未解決事項がある場合は、原本照合を完了扱いにしない。

年末調整未済という指定と、年末調整済みでのみ記載する合計額等が併存する場合は、`status=incomplete`と`WS_YEAR_END_STATUS_CONFLICT`を返して確認へ戻す。これはどちらの値が誤っているかを自動判定するものではない。矛盾が解消するまでws-saveは保存を拒否し、計算への採用も行わない。

最低限、`WS_DEDUCTION_TOTAL_MISMATCH`、`WS_FIELDS_UNCONFIRMED`、`WS_SOURCE_NOT_CONFIRMED`、`WS_FISCAL_YEAR_MISMATCH`、`WS_INVALID_INNER_AMOUNT`を区別する。内書きが総額を超える場合は最後のエラーとする。照合用の派生額が正で、根拠メモがない場合も未確認として扱う。

**限界:** 二つの欄の値を完全に交換すると合計は変わらない。同額の取り違えも合計では検出できない。`matched`を「OCRが正しい」と表示せず、原本の二つのラベルと、それぞれの枠内の金額を再照合する。検算は税務上の適用要件を証明するものでもない。

### 5.2 コマンドの変更

| コマンド | 契約 |
|---|---|
| `import withholding --file-path PATH` | ファイル確認・テキスト抽出という役割を維持する。未読金額はnullで返し、成功を読取り完了と扱わない。`WithholdingSlipData`を使って出力定義のずれを防ぐ |
| `ledger ws-check --fiscal-year YEAR --input FILE` | 新規の読取り専用コマンド。`WithholdingSlipInput`を受け取り、検算結果を返す。DB引数は不要 |
| `ledger ws-save --db-path DB --fiscal-year YEAR --input FILE` | 平坦な`WithholdingSlipInput`を受け取り、共通検算を実施してから保存する。戻り値へ`validation`を追加する |
| 同上の`--withholding-slip-id ID` | 任意の新オプション。同じ年分の既存行を全項目置換し、IDを保持する。未指定なら従来どおり追加する。別年分・存在しないIDは拒否する |
| `ledger ws-list` | 既存の一覧形式とIDを維持し、各行へ再計算した`validation`を追加する |
| `ledger ws-delete` | 現行の契約を維持する |

入力例に`detail`や`fiscal_year`のラッパーを設けない。原本の年分は別の意味を持つ`document_fiscal_year`で表す。

型エラー・年分不一致・内書きの矛盾・計算可能な控除合計の不一致は、`ws-save`では保存せず、既存の`status=error`・`message`・終了コード1に従う。`code`と`validation`を追加し、原本へ戻れる項目名と差額を返す。推測した修正値を自動保存しない。

未確認を含む票は、証憑の下書きとして保存できる。戻り値は保存成功でも`ready_for_calculation=false`とし、申告用データへ採用しない。既存行の訂正も検算後に一つのトランザクションで行い、失敗した場合は旧行を保持する。実データの保存・訂正は確認済みの対象内容に限る。

`ws-check`では、JSON自体が不正なら終了コード1とする。有効な入力に対する`mismatched`や`incomplete`は検査結果として終了コード0で返す。出力の外側は`status=ok`、`fiscal_year`、`validation`を持ち、検算の状態は`validation.status`に置く。呼出し側は終了コードだけでなく`validation`を判定する。

### 5.3 申告計算との接続

```mermaid
flowchart LR
    A[原本・テキスト] --> B[reading-withholdingによる構造化]
    B --> C[ws-checkによる検算]
    C --> D[原本との照合と対象内容の確認]
    D --> E[ws-saveによる保存]
    E --> F[ws-listによる読戻しと再検算]
    F --> G[申告入力の組立て]
    G --> H[既存のcalc-income]
    H --> I[DB照合付きsanity-check]
    I --> J[e-taxへの転記一覧]
```

`ready_for_calculation=false`の票から申告入力を作らない。支払金額は`salary_income`へ、源泉徴収税額は`withheld_tax`へ渡す。`salary_income_after_deduction`は原本照合のために残し、`salary_income`へ代入しない。

源泉徴収票の`social_insurance`から内書きの小規模企業共済等掛金を差し引いた額を、申告入力の社会保険料の一部とする。別途支払った社会保険料を、重複を除いて加える。内書きの掛金は種類を確認して既存のiDeCo等の入力へ渡し、給与分と証明書分を二重加算しない。種類や重複を確認できなければ、申告入力の組立てを止める。

配偶者・扶養・特定親族・基礎控除の記載額は照合用である。申告時には本人と親族の事実、全所得、年分から既存の計算関数が算出する。生命保険料控除額を保険料の入力欄へ渡すこともしない。

複数枚では、前職分を通算した票と通算前の票を重ねて集計しない。どの票を年間の給与の根拠として選んだかを明示する。氏名や金額だけによる自動除外は行わない。

### 5.4 DB照合付きsanity-check

既存の`{input, result}`へ、任意の`salary_evidence`を追加する。これは税額計算の入力ではなく、証憑照合の条件である。

| 項目 | 型と意味 |
|---|---|
| `slip_ids` | 1件以上で、重複のない正の厳密な整数のリスト。照合対象の票を指定する |
| `selection_confirmed` | `StrictBool \| None`。年間の給与を網羅し、前職分等の重複を除いた選択だと確認した場合にtrueにする |
| `additional_social_insurance` | 非負の厳密な`int \| None`。選択した票に含まれない、確認済みの社会保険料。追加分がなければ明示的な0とする |

`--db-path`があり、給与収入または給与の源泉税額が0以外の場合は、この条件がなければ`SALARY_EVIDENCE_UNCONFIRMED`を返す。`salary_evidence`が指定された場合は、給与額が0でも照合する。選んだ票の存在、対象年、原本確認、共通検算の状態を調べる。

`calculation_mode=filing`では、選択や必要項目が未確認ならerrorとして申告前検査を不合格にする。`estimate`では同じ不足をwarningで明示し、仮定した金額が明示的に与えられた試算はできるようにする。不明な値を自動で0へ埋めることは、試算でもしない。対象年の不一致や、揃った金額どうしの不一致は、モードにかかわらずerrorとする。warningだけで検査の`passed`がtrueでも、証憑照合済みや申告準備完了とは表示しない。

必要な情報が揃った場合だけ、次の等式を照合する。

```text
input.salary_income = 選択した票のpayment_amountの合計
input.withheld_tax = 選択した票のwithheld_taxの合計
input.social_insurance
  = 選択した票の(social_insurance - social_insurance_small_business_mutual_aid)の合計
  + salary_evidence.additional_social_insurance
```

不一致は`SALARY_AMOUNT_LEDGER_MISMATCH`、`SALARY_WITHHOLDING_LEDGER_MISMATCH`、`SALARY_SOCIAL_INSURANCE_LEDGER_MISMATCH`に分ける。nullを`SUM`の無視や`COALESCE(..., 0)`で消さない。結果の源泉税額も照合する。DBを初期化・移行せず、存在確認後に既存の接続関数で読み取り、論理内容を変えない。

照合に必要な新列がない旧DBでは、移行が必要な旨をエラーとして返す。検査の途中で移行を実行したり、新列がないことを0・確認済みと読み替えたりしない。

`salary_evidence`を与えたのにDBがない場合は入力エラーとする。DBなしの既存の単発計算・sanity-checkは従来どおり使えるが、証憑との一致を確認したことにはならない。`calc-income`へ手書きの数値を渡す経路を、この変更だけで完全に禁止できるとは説明しない。

掛金の種類への配分、票に含まれる国民年金と別資料との重複、家族の適用要件等は、この三つの等式だけでは証明できない。申告入力を確定する既存手順で確認する。検算結果を改ざん防止の証明や署名として扱う機構は追加しない。

## 6. DB移行と互換性

新規DBでは、既存金額列をnullableかつ`DEFAULT NULL`にし、新規金額列も同じ定義にする。`document_fiscal_year`、二つの確認フラグ、`deduction_derivation_note`はnullableな列として追加する。`blank_fields`は検証済みのリストをJSON文字列で保存するnullableなTEXT列とし、SQL上のNULLはAPIで空リストに対応付ける。確認フラグにはNULL・0・1だけを許す。

旧列の`NOT NULL DEFAULT 0`を外すにはテーブルの再構築が必要である。[db.py](../src/shinkoku/db.py)の既存の固定資産移行と同じ方式で、`schema.sql`を定義の正本にし、既存の外側のトランザクションとSAVEPOINTを利用する。

1. 旧スキーマを識別する。未知の列構成は自動で捨てず、移行を止める。
2. 新しい一時テーブルを作り、既存の全列を名前を指定してコピーする。
3. 件数・ID・年分・全旧値・`created_at`の一致を確認する。
4. テーブルを置き換え、既存の索引・トリガーとAUTOINCREMENTの採番上限を保持する。
5. 外部キーを検査し、全移行の成功後に確定する。中断時は旧状態へ戻す。再実行は何も変えない。

旧値に新しい型・範囲制約へ適合しないものがある場合は、値を変更して移行を続行せず、旧データを保持して中断する。移行も通常の保存も、SQLiteのWALと外部キーを維持する。既存行の訂正では元の`created_at`を保持する。

旧DBの0が「読めた0」か「未読の既定値」かは復元できないため、**既存の0を一律にNULLへ変えない**。旧値は保持し、新しい原本確認情報はNULLのままにする。再確認されるまで`ready_for_calculation=false`である。再確認が必要になるのは申告に使用する票を選択したときであり、旧DBを開くために全票を確認し直すことは要求しない。新しい入力で省略された金額はNULLになる。

既存の平坦なJSONと既存のコマンド名は受け付けるが、省略値の意味と一部の出力型は変更される。この変更を「完全な互換」とは呼ばない。CLI契約、リリースノート、バージョンを[開発規約](development-contracts.md)に従って更新する。既存の明示的な金額と税額計算の結果は変えない。

追加コマンドは`ws-check`の1件であり、調査時点の109件から110件になる想定である。実装時点の基準件数を再確認し、[契約ヘルパー](../tests/helpers/cli_contract.py)と[スナップショット](../tests/fixtures/cli_contract.json)を意図した変更として更新する。型の検査を緩めて既存テストを通さない。

## 8. テスト計画と完了条件

### 8.1 架空fixture

将来の実装時に`tests/fixtures/withholding/`へ、原本PDF・PNG・読取りの期待JSON・検算の期待JSON・根拠を記したREADMEを置く。画像には架空資料である旨を欄外に示し、名前は「架空受給者」、勤務先は「架空勤務先」とする。マイナンバーや実在の住所は使わない。

再現の中心は、二つの隣接欄に異なる額を入れた2025年分とする。例えば特定親族特別控除610,000円、社会保険料等750,000円、基礎控除680,000円、その他の所得控除0円なら、控除合計の独立期待値は2,040,000円である。社会保険料等だけを610,000円へ誤読した負例は、内訳1,900,000円、差額-140,000円となる。

これは検算のfixtureの定義であり、現行の読取りが実際にこの誤りを出したという記録ではない。全票の給与・年税額・親族の設定を作る際には、2025年分の資料で矛盾がないことを確認して凍結する。期待値を製品の計算結果から生成しない。[2025年分の基礎控除・特定親族特別控除の表、56ページ](https://www.nta.go.jp/publication/pamph/gensen/nencho2025/pdf/115.pdf)

2026年分には別の期待値を置く。年末調整時の本人の合計所得金額を4,000,000円とし、両年とも居住者で、特定親族の適用要件を満たす22歳の親族の合計所得金額を880,000円、社会保険料等を750,000円、その他の所得控除を0円とした確認例では、次の差がある。2026年分は通常の12月の年末調整を前提にする。

| 年分 | 基礎控除 | 特定親族特別控除 | 控除合計の独立した計算 | 根拠 |
|---|---:|---:|---|---|
| 2025年分 | 680,000円 | 610,000円 | 750,000 + 610,000 + 680,000 = 2,040,000円 | NTA-2025-TABLE、56ページ |
| 2026年分 | 1,040,000円 | 610,000円 | 750,000 + 610,000 + 1,040,000 = 2,400,000円 | NTA-2026-TABLE、56ページ |

この数値は年分の取り違えを防ぐfixtureの期待値であり、新しい計算用の控除表を定義するものではない。共通検算は原本の額の算術上の整合性を調べるものであり、年分だけからこの例の額を実際の票へ強制する機能は作らない。年途中の票と申告時の控除額が異なる場合は、NTA-2026-TIMINGの適用関係を確認する。

### 8.2 自動テスト

| 分類 | 必須の検証 |
|---|---|
| モデルと往復 | 未読のNULL、原本で空欄、明示的な0を区別する。falseと未確認を区別する。省略、未知キー、boolの金額、数値文字列、負数、空欄との矛盾を検査する |
| 控除合計 | 正常な一致、特定親族の欠落、社会保険料等の取り違え、内書きの二重加算、住宅ローン控除の誤加算、年分不一致を検出する |
| 不完全な票 | 年末調整済みで合計や内訳が不明ならincompleteにする。年末調整未済の適切な空欄はnot_applicableにする。不明な年末調整状態をfalseにしない |
| 年分と適用時点 | 2025年分と2026年分に別の一次資料・独立期待値を持たせる。帳票の欄配置が同じでも期待値を共用しない。年途中の記載額を現在の控除表へ自動修正しない |
| 検出限界 | 二つの額を交換して合計が同じになる場合は、合計だけでは不一致を検出できないことを明示する。原本未照合のままreadyにしない |
| 保存と訂正 | 型・整合性エラーではDBを変更しない。未確認の保存は下書きとして読戻す。同じIDの全項目更新、別年度の拒否、失敗時の旧値保持を確認する |
| 旧DB移行 | 非空DB、複数年分、明示値と旧デフォルト0、NULLの追加列、ID・作成日時・索引・採番上限の保持、再移行、中断後のロールバックを確認する |
| DB照合 | 明示的に選んだ票だけを照合する。選択の未確認、重複ID、存在しないID、別年分、未確認の票、給与・源泉・社会保険料の各不一致を検出する。未確認の不足はfilingでerror、estimateでwarningとし、金額の不一致は両方でerrorにする |
| CLIとSkill | 入力モデルへのstrict検証、エラーJSON、終了コード、110件を想定した契約更新、読取りから保存まで形式調整が不要であることを確認する |
| 結合 | 実CLIで読取り済みJSON→検算→保存→読戻し→filing計算→DB付きsanity-checkを通す。読取り誤りを注入した経路が不合格になることも確認する |
| 既存回帰 | 太郎の49項目、二郎の45項目、R6・R7、固定資産台帳の既存テストを維持する |

二郎の既存fixtureへ確認情報を補う場合は、凍結済みの金額・人物設定を変えない。既存資料で確定できる項目だけを、根拠を示した補助データとして追加する。不明な項目をテスト都合で0や確認済みにせず、不足する場合は独立した新fixtureで新経路を検証し、既存ケースの未確認範囲を報告する。

### 8.3 画像読取りの検証

実装前後で同じ架空PDF・PNGを使用し、ラベルと金額、内書き、空欄を読み取らせる。元画像・期待JSON・実際の読取り結果・使用した読取手段・照合結果を、`playground/withholding-validation/`へ残す。少なくとも、特定親族あり、特定親族なし、年末調整未済、二つの隣接欄が読みづらい画像を含める。

改修前の読取りが偶然正しかった場合は「誤読を再現した」と報告しない。誤読済みJSONを使う決定的な負例と、画像を使う評価は別の結果として記録する。修正後に未読をNULLで止める結果も、安全な結果として正しい金額を読めた場合とは区別する。

外部モデルを使う画像評価は通常のpytestの成功条件に混ぜない。ただし、画像評価が未実施なら「読取りの修正を検証済み」としてリリースを完了しない。読取手段が利用できなければ、依存ソフトの無断導入はせず、検証できていない範囲を報告する。複数エージェントによる読取りは、この会話での明示的な依頼がある場合だけ行う。

## 9. 実装の順序

設計レビュー後は、次の順に、各段階を検証可能な変更として進める。

1. **再現資料と負例を固定する。** 架空帳票・独立期待値を作り、現行の情報欠落、未読0、誤読済みJSONの検査不足を確認する。現行の画像評価結果も残す。
2. **共通の型と検算を作る。** nullableな金額、空欄、確認情報、合計検算、`ws-check`を実装する。単体・CLI・strict契約のテストを通す。
3. **保存と移行をつなぐ。** 旧DBの再構築、`ws-save`の検算とID指定による更新、`ws-list`での再検算、importのNULL出力を実装する。移行・中断・往復を検証する。
4. **申告の経路をつなぐ。** DB付きsanity-checkとSkillの入力組立て・転記一覧を更新する。給与の負例、既存の二人物の回帰、画像評価を実施する。

実装を途中の状態でリリースせず、変更後の型・保存・Skillを揃える。税額計算の式や税制定数の変更が必要に見えた場合は、この作業へ混ぜず、根拠と影響を別の欠陥として報告する。

最終検査は、`uv run pytest tests/ --basetemp playground/pytest-withholding`、`uv run ruff check src/ tests/`、`uv run ruff format --check src/ tests/`、`uv run mypy src/shinkoku/ --ignore-missing-imports`を使用し、所要時間を記録する。使い捨てDB・設定だけで実行する。

## 10. レビューで確認する判断

以下をこの案の推奨方針とする。実装を始める前に、この文書をレビューする。

1. 省略値を0からNULLへ変更する。既存データは値を保持し、申告に選択した票だけを再確認する互換性変更を受け入れる。同じ票の同じ内容への確認を繰り返さない。
2. 未確認の票を下書きとして保存できるようにし、`ws-save`への任意ID指定で安全に訂正できるようにする。
3. 初版の人数・区分からの照合額は、根拠付きで確認する範囲に絞る。人数欄の自動認識・自動換算は追加しない。
4. DB付きsanity-checkで給与の照合対象を明示させ、不足時には申告前検査を不合格にする。試算では不足を警告し、単発の税額計算を証憑検証済みとは扱わない。

税務上の項目と期待値には第2.3節の公的資料を使う。上の4点の保存・確認・停止方法は第2.4節に示したソフトの設計判断であり、国税庁や財務省が指定した操作手順とは説明しない。
